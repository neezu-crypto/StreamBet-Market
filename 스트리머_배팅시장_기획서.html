스트리머 배팅시장 — 방송 중 실시간 이벤트에 배팅하는 가상 재화 게임 · 기획서
재화 가상 재화 (현금성 없음) 스택 Firebase RTDB + GitHub Pages 초기자산 1,000,000
01

개요

방송 중 실시간으로 발생하는 이벤트에 시청자들이 가상 재화로 배팅하는 게임. 방송 내용은 예측이 불가능하고 실시간으로 변하기 때문에, 정해진 배팅 항목뿐 아니라 유저가 직접 배팅 주제를 제안할 수 있는 구조를 핵심으로 한다.

기존 프로젝트와의 관계 — SOOP STOCK 등 기존 게임과 기술 스택을 공유하지만, 자산 시스템은 독립적으로 운영한다.
02

배팅 주제 카테고리

사전 정의 카테고리 (자동 · 반자동 판정)

구분예시판정 방식
게임 방송이번 판 승/패, 킬수 구간, 목표 달성 여부스트리머 확정 · 다수결
토크 · 저챗키워드 발언 여부, 후원 금액 구간스트리머 확정
시청자 지표N분 후 시청자 수 증감, 채팅량 목표API 연동 자동 판정
합방 · 대결스트리머 간 승부, 미니게임 결과스트리머 확정 · 다수결

초기 버전은 자동 판정이 가능한 카테고리부터 우선 구현하여 판정 시비 리스크를 최소화한다.

유저 제안형 배팅 (자유입력 방식)

배팅 주제 내용은 자유 텍스트로 입력한다. 다만 판정 가능성을 담보하기 위해 아래 항목은 제안 시 필수로 함께 지정한다.

예: 봉준이 20분 안에 랭크 1위를 달성할 것이다

제안 시 함께 지정: 배팅 마감 시점이벤트 마감 시점

판정 방법은 제안 시 선택하지 않는다 — 04번의 관리자 · 인증 스트리머 검증과 좋아요 다수결은 둘 중 하나를 고르는 게 아니라 둘 다 자동으로 동시에 적용되는 병렬 게이트(먼저 조건을 채우는 쪽으로 통과)다. 그래서 제안 화면에는 판정 방법 선택 항목이 없다.
참가 스트리머 지정은 예외 — 배팅 주제 문구 자체는 자유입력이지만, 주제에 연결되는 스트리머 지정 필드는 자유입력이 아닌 선택형이다. 자세한 내용은 05번 참고.
본인 제안 배팅 참여 허용 — 시크릿 창 등 우회 접속이 어차피 가능한 웹게임 특성상, 원천 차단보다는 배팅 한도 등 완화 장치로 대응한다.
03

대전 유형

배팅 주제 개설 시 아래 3가지 유형 중 하나를 선택한다. 개인전 · 1vs1은 이진 판정, 단체전은 다중 판정으로 정산 로직이 달라진다.

유형대상결과 형태배당 계산
개인전스트리머 1인의 승부 (예: N시간 안에 X 가능/불가능)성공 · 실패 (이진)찬성/반대 두 풀로 단순 분배
1vs1 대전스트리머 vs 스트리머승 · 패 (이진)두 풀로 단순 분배
단체전여러 스트리머 추가 후 1위 예측순위 (다중)N개 풀로 분산, 배당 편차 큼

단체전 설계 시 고려사항

  • 배당 편차 — 인기 스트리머에 배팅이 몰리면 배당이 낮아지고 비인기 스트리머는 배당이 치솟는 패리뮤추얼 구조. 몰빵 방지를 위해 최소 배당 하한선 검토
  • 참가자 변경 — 방송 중단 등으로 중도 이탈/추가 가능성 → 배팅 마감 시점 이후 참가자 목록 고정
  • 순위 판정 기준 명시 — 시청자 수 1위 / 게임 순위 1위 / 스트리머 자체 선언 등, 검증 단계에서 판정 기준을 템플릿에 필수 입력

템플릿 필드 (대전 유형 공통)

대전 유형 : [개인전 / 1vs1 / 단체전] 참가자 : [스트리머 1명 / 2명 / N명 (단체전만 추가 가능)] 판정 기준 : [자유 텍스트 또는 사전 정의 항목 선택] 판정 방법 : 자동 적용 (관리자·인증 스트리머 검증 OR 좋아요 다수결, 04번) — 제안 시 선택 불필요 시간 구조 : [배팅 가능 시간 / 배팅 마감 / 이벤트 시작·마감]
04

배팅 주제 검증 프로세스

유저 제안 배팅은 오픈 전 검증 단계를 거친다. 검증 방식은 2가지 중 선택:

  1. 관리자 / 인증 스트리머 직접 검증
  2. 다수 익명 계정의 '좋아요' 수 통과 (라이트 검증, 실시간성 확보) — 좋아요 10개 이상 시 통과
주제 제안 (자유입력) │ ▼ 검증 (관리자 · 인증 스트리머 승인 OR 좋아요 다수결 통과) │ ▼ 배팅 오픈 → 배팅 마감 → 이벤트 진행 → 정산
관리자 · 인증 스트리머는 검증 단계 생략 — 제안자 본인이 관리자이거나 05번 기준 인증 스트리머라면 검증 단계 없이 즉시 배팅 오픈으로 넘어간다. 10번에서 정한 최종 승 · 패 판정 권한자(관리자 · 인증 스트리머)와 동일한 기준이다 — 어차피 판정 권한을 가진 사람이 올린 제안을 별도로 검증받게 하는 건 의미 없는 절차다. 단, 최종 승 · 패 판정(10번) 자체는 이 경우에도 생략되지 않고 그대로 필요하다.

금지 주제 (사전 경고 없이 삭제)

검증 통과 여부와 무관하게, 아래에 해당하는 주제는 관리자가 사전 경고 없이 삭제할 수 있다. 제안 화면에도 동일한 목록을 안내한다.

  • 스트리머 비하
  • 평가 불가능한 주관적인 주제
  • 사회적 · 정치적 뉴스 주제
  • 방송 송출 시 주의가 필요한 주제 (선정성 · 혐오 표현 등)
  • 특정 개인(스트리머 외) 사생활 · 명예훼손 소지가 있는 주제
  • 실제 금전 · 도박을 암시하거나 유도하는 주제
  • 불법행위를 조장하거나 미화하는 주제
  • 특정 집단에 대한 차별 · 혐오 표현이 포함된 주제

유저 신고 기능

관리자 · 인증 스트리머가 능동적으로 찾아야만 금지 주제를 걸러낼 수 있는 건 아니다. 모든 배팅 카드(대기중인 제안 포함)에 신고 버튼을 두어, 유저가 직접 위 8개 금지 주제 항목 중 하나(또는 기타)를 사유로 골라 상세 내용과 함께 신고할 수 있다.

  • 접수함 처리 권한 — 관리자와 인증 스트리머 모두 관리 탭의 "신고 접수함"에서 신고 내역을 확인하고 처리할 수 있다. "스트리머 인증 관리"(05번)처럼 관리자 전용으로 좁히지 않는다 — 신고 처리는 마켓 관리(10번)의 연장선이라 인증 스트리머가 이미 갖고 있는 권한 범위와 같기 때문이다
  • 처리 방법 — 신고 건에서 바로 해당 마켓의 관리 · 검수 화면으로 이동해 조기 마감 · 무효 처리 · 판정 확정(10번) 또는 검수 승인 · 반려(04번)를 그대로 수행하거나, 문제 없다고 판단되면 "확인 완료"로 종료
  • 신고됐다고 바로 숨기지 않는다 — 신고가 접수돼도 관리자 · 인증 스트리머가 검수하기 전까지 해당 마켓은 계속 노출되고 배팅도 그대로 가능하다. 검수 결과 무효 처리로 판단되면 그 시점부터 08번 규정대로 참가자 전원의 배팅이 취소 · 전액 환불된다

신고 남용 방지

  • 마켓당 중복 신고 금지 — 한 유저가 같은 마켓을 신고할 수 있는 건 1회뿐이다. 이미 신고했다면 재신고 불가
  • 신고 간 쿨다운 5분 — 서로 다른 마켓에 대한 신고끼리는 5분 간격을 둬야 한다. 봇 · 스크립트로 짧은 시간에 여러 마켓을 무더기로 신고하는 행위를 차단
  • 신규 계정 신고 대기 10분 — 계정 생성 후 최소 10분이 지나야 신고 가능하다. 09번의 배팅 · 환전 1분 대기보다 길게 잡은 이유는, 배팅은 재화를 걸어야 해서 어뷰징에 자체 비용이 들지만 신고는 공짜 행동이라 즉석 다중 계정으로 악용하기 쉽기 때문이다
왜 인증 스트리머에게도 열어두나 — 신고된 마켓을 처리하려면 결국 마켓 관리 권한(조기 마감 · 무효 처리 · 판정)이 필요한데, 이건 인증 스트리머도 이미 갖고 있는 권한이다(10번). 신고함 열람만 관리자로 좁히면 오히려 인증 스트리머가 처리하려 할 때 신고 내용을 못 봐서 불편해진다.
이의제기 프로세스는 두지 않는다 — 신고 처리(무효 · 반려 등)가 04번 금지 주제 기준과 09 · 10번 운영 원칙에 따라 이뤄지는 이상, 관리자 · 인증 스트리머의 판단이 최종이다. 별도 이의제기 절차 없이 처리 결과를 그대로 확정한다.

검수 화면 (관리자 · 인증 스트리머 전용)

"대기중인 제안" 목록에서 카드를 클릭하면 검수 모달이 뜬다. 기본은 자동 기준(좋아요 10개, 09번 최소 참여자 5명)을 그대로 따르되, 검수자가 아래 조건을 개별적으로 예외 처리할 수 있다.

  • 추천수 미달 강제 승인 — 좋아요 10개를 못 채웠어도 검수자가 직접 승인하면 즉시 오픈
  • 참가자 미달 강제 정산 — 09번 최소 참여자 수(5명)를 못 채웠어도, 검수자가 설정하면 무효 · 환불 처리하지 않고 정상 정산 진행
왜 예외를 허용하나 — 자동 기준은 일반적인 어뷰징 방지용이지만, 실제로는 특정 소수 인원만 관심 있는 마니아성 주제(예: 특정 팬덤 이벤트)도 있을 수 있다. 검수 권한자가 상황을 보고 예외를 줄 수 있게 하여 지나치게 경직된 자동화를 보완한다.
05

스트리머 인증 시스템

인증 여부의 최종 데이터는 주식시장과 공유하는 streamerVerifications 노드를 그대로 쓴다. 신청 접수 UX는 배팅시장에 자체로 두되, 승인된 결과는 로컬에 따로 저장하지 않고 공유 노드에 기록한다.

보안 규칙을 완화한 이유 — streamerVerifications는 원래 .read: false로 잠겨 있었다. 하지만 배팅시장과 주식시장은 같은 Firebase 프로젝트, 같은 Security Rules 파일을 공유하는 사이라, 두 서비스 모두에 적용되는 규칙을 완화하는 것 자체는 문제가 없다고 판단해 .read를 true(또는 auth != null)로 열기로 했다. 노드에 담긴 정보(닉네임 · uid · 인증 시각)가 민감 정보가 아니라 열어도 안전하다. 쓰기(write)는 기존처럼 클라이언트 차단, Admin SDK(Functions)만 가능하도록 유지한다.
  1. 스트리머가 닉네임 + SOOP 아이디를 입력해 신청 (배팅시장 자체 모달). 입력한 SOOP 아이디로 홍보 배너 이미지를 실시간 미리보기 가능
  2. 관리자가 관리 탭에서 신청 목록을 검수해 승인 · 반려. 승인 시 Cloud Functions가 공유 노드 streamerVerifications에 기록하고, 즉시 양쪽 서비스 모두에서 인증 상태가 반영된다
  3. 관리자는 이미 인증된 스트리머도 관리 탭에서 인증 해제할 수 있다 (공유 노드에서 제거, 배너에서 즉시 사라짐)
uid가 바뀐 경우 재신청 — 계정 문제 등으로 인증된 스트리머의 uid가 바뀌어 04 · 10번 권한이 박탈되더라도, 동일한 SOOP 아이디로 재신청하면 다시 인증받을 수 있다. 판별 키는 SOOP 아이디이므로, 관리자가 승인하면 기존 streamerVerifications 레코드를 새로 만들지 않고 uid 필드만 최신 값으로 갱신한다(닉네임 · 인증 이력은 유지). SOOP 아이디가 같은 사람이 계속 재신청하는 걸 막을 이유가 없으므로, 닉네임 · SOOP 아이디 중복은 신청 차단 사유가 아니다.

인증된 스트리머는 다음 권한을 얻는다:

  • 모든 배팅 주제에 대한 검증 · 판정 권한 (04, 10번 갱신 — 최초 설계는 "본인 방송 관련 주제"로 한정했으나, 실제로는 인증 스트리머 전체에게 모든 주제에 대한 권한을 부여하는 쪽으로 확정했다. 인증 스트리머 수가 적은 초기에는 특정 스트리머 관련 주제만 아무도 판정 못 하고 방치되는 상황을 막기 위함)
  • 배팅시장 메인페이지 홍보 배너에 본인 방송국 노출
인증 신청 · 승인 · 해제는 관리자 전용 — 인증 스트리머는 모든 배팅 주제를 검증 · 판정할 권한은 있지만, 다른 스트리머의 인증 신청을 승인 · 반려하거나 인증을 해제할 권한은 없다. 이 부분은 관리 탭에서도 "관리자 전용 · 인증 스트리머 열람 불가"로 별도 표시한다.
주식시장 쪽 영향 — 규칙 완화와 신규 기록 위치는 공유 파일 수정이므로 주식시장 서비스에도 그대로 적용된다. 주식시장이 이 노드를 다른 용도로 참조 중이라면 함께 검토가 필요하다.

배팅 대상 스트리머 지정 (선택형, 자유입력 아님)

배팅 주제에 참가 스트리머를 지정할 때는 자유 텍스트가 아니라, SOOP STOCK(스트리머 주식시장) 서버와 공유하는 동일 Firebase RTDB에 이미 등록된 닉네임 중에서 선택하는 방식으로 한다.

  • 참조 데이터 — stocks/{id}/name 전체 상장 스트리머 닉네임 목록 (자동완성 · 드롭다운 후보)
  • 인증 배지 매칭(닉네임 기준) — 목록에 표시된 스트리머 카드에 공유 streamerVerifications의 닉네임을 대조해 "✓ 인증" 배지를 표시 (규칙 완화로 클라이언트가 직접 조회 가능)
  • 본인 권한 판별(uid 기준) — 로그인한 유저 본인이 인증 스트리머인지는 닉네임이 아니라 streamerVerifications의 uid를 auth.uid와 대조해 판별한다. 04번 검증 생략, 10번 판정 권한, 관리 탭 노출 여부가 전부 이 값을 기준으로 결정된다
  • 접근 권한 — 배팅시장 클라이언트는 stocks · streamerVerifications 모두 읽기 전용으로만 조회하며, 쓰기 권한은 갖지 않는다 (자산 시스템 분리 원칙과 동일하게, 참조 데이터 공유가 두 게임 로직에 간섭하지 않도록)
  • 미상장 스트리머 처리 — 목록에 없는 신규 스트리머는 배팅 대상으로 지정 불가. 먼저 주식시장 쪽 상장 신청(listingRequests) 절차를 거쳐야 함
왜 선택형인가 — 자유입력 시 오타·표기 차이로 동일 스트리머가 여러 이름으로 파편화되어 배팅 주제가 흩어지는 문제를 방지. 이미 검증된 스트리머 마스터 데이터(주식시장 상장 목록)를 재사용해 별도 등록 절차 없이 정합성을 확보한다.

배팅 풀 구조

배팅 풀은 패리뮤추얼(pari-mutuel) 방식을 기본으로 채택한다. 고정 배당률(북메이커) 방식은 플랫폼이 카운터파티로서 손실 위험을 직접 떠안아야 하는데, 유저가 자유롭게 주제를 제안하는 구조(02번)에서는 오즈메이킹 부담이 너무 크다. 패리뮤추얼은 참가자들이 낸 재화를 참가자끼리 나눠 갖는 구조라 플랫폼 리스크가 없고, 03번에서 단체전에 이미 전제한 방식과도 일치한다.

배당 계산 공식

배당 배수 = ( 전체 풀 합계 × (1 − 수수료율) ) ÷ 승리 outcome 풀 합계 지급액 = 배팅액 × 배당 배수

개인전 · 1vs1은 outcome이 2개(성공/실패, 승/패)이고, 단체전은 참가자 수만큼 N개의 outcome 풀로 나뉜다. 배팅 마감 전까지는 실시간 풀 비율을 기준으로 한 추정 배당률만 노출하고, 확정 배당률은 배팅 마감 시점의 풀로 고정한다(06번 시간 구조와 연동).

수수료(레이크)

구분내용
수수료율5% — 전체 풀에서 정산 전 차감. 경마 · 카지노(15~25%)와 달리 실이익이 아닌 재화 회수가 목적이므로 낮게 시작
용도재화 회수(sink) 창구로 사용해 인플레이션을 관리. 일부를 잭팟 · 이벤트 재원으로 전환하는 안도 검토 가능

최종 확정치 — 더 이상 재조정하지 않는다.

최소 배당 하한선

승리 outcome에 배팅이 지나치게 쏠려 배당 배수가 1배 미만(원금보다 적게 돌려받는 경우)이 되는 것을 막기 위해 하한 배수 1.1배를 둔다. 1.05배는 승리해도 체감 보상이 약하고, 1.3배 이상은 쏠림 상황마다 수수료 재원을 빠르게 고갈시키므로 1.1배를 균형점으로 잡았다. 공식상 배당이 하한보다 낮으면 하한을 적용하고, 부족분은 수수료로 적립해 둔 재원에서 충당한다. 재원이 부족하면 하한을 적용하지 않고 공식값 그대로 지급해 재원 고갈을 막는다.

무효 · 환불 처리

  • 승자 없음 — 승리 outcome에 걸린 배팅이 하나도 없으면(풀 0) 배당 계산 자체가 불가능하므로 전체 배팅 전액 환불
  • 최소 참여자 수 미달 — 09번(어뷰징 방지) 조건과 동일하게 전액 환불
  • 이벤트 자체 무산 — 방송 종료 · 판정 불가 등으로 이벤트가 성립하지 않은 경우 전액 환불

단체전(N-outcome) 추가 규칙

  • 03번에서 지적한 배당 편차 문제는 위 최소 배당 하한선으로 1차 완화
  • 배팅 마감 시점 이후 참가자 목록 고정 — 마감 후 중도 이탈한 참가자가 최종 결과 판정에서 제외되면 해당 참가자의 outcome 풀만 무효 처리 후 전액 환불하고, 나머지 outcome은 정상 정산
고정 배당률 방식은 완전히 배제하는가 — 아니오. 02번의 사전 정의 카테고리처럼 자동 판정이 확실하고 표본이 쌓인 주제에 한해서는 추후 별도 검토 가능. 다만 초기 버전은 패리뮤추얼 단일 구조로 시작한다.

정산 방식

유형정산 방법
자동 판정형 (시청자 수 등)백엔드 자동 정산
유저 제안형관리자 또는 인증 스트리머만 판정 가능. 05번 갱신 — 인증 스트리머는 본인 방송 관련 주제로 한정하지 않고 모든 유저 제안형 마켓을 판정할 수 있다

판정 확정 후 08번 배팅 풀 구조의 공식에 따라 배당 배수를 계산하고 자동 지급한다.

정산 결과 확인은 "정산 내역" 탭 — 별도 인앱 알림(푸시 등) 대신, 상단 네비게이션에 전용 "정산 내역" 탭을 두어 유저 본인의 모든 배팅 결과(적중 · 미적중 · 무효 환불, 지급액, 순손익)를 한곳에서 확인하게 한다. 요약 통계(총 정산 건수 · 총 배팅액 · 총 지급액 · 순손익)를 상단에 먼저 보여주고, 개별 결과 목록이 그 아래 이어진다.
채팅 다수결을 판정에서 제외한 이유 — 04번의 '좋아요 다수결'은 배팅을 열지 말지 정하는 제안 검증 단계용 라이트 검증이고, 실제 재화가 오가는 최종 승/패 판정은 브리게이딩(봇 · 다중계정 조작)에 취약해 다수결로 맡기기엔 위험이 크다. 그래서 판정 권한은 관리자 · 인증 스트리머로 한정한다.
운영 부담 트레이드오프 — 인증 스트리머가 본인 관련 주제로 한정됐던 최초 설계였다면 미인증 스트리머 관련 배팅이 늘어날수록 관리자 부담이 커졌겠지만, 05번 갱신으로 인증 스트리머 누구나 모든 마켓을 판정할 수 있게 되면서 이 부담이 인증 스트리머 전체에 분산된다. 다만 그만큼 인증 스트리머 개개인에게 강한 권한이 열려있으므로, 05번의 인증 승인 절차(관리자 검수)가 더 중요해진다.

마켓 관리 조작 (조기 마감 · 무효 처리)

진행중인 마켓 카드를 클릭하면 관리자 · 인증 스트리머만 접근 가능한 관리 화면이 뜬다. 판정 확정 외에도 조기 마감과 무효 처리(전액 환불)를 수행할 수 있는데, 재화가 걸린 강한 권한이라 아래 두 가지를 필수로 남긴다.

  • 사유 선택 필수 — 자유 텍스트가 아닌 사전 정의된 사유 목록에서 선택. "운영 사유"(조기 마감: 이벤트 조기 종료 · 방송 종료 · 어뷰징 의심 · 기타 / 무효 처리: 최소 참여 인원 미달 · 이벤트 무산 · 주제 오류 · 어뷰징 적발 · 기타)와 "금지 주제 위반"(04번 8개 항목) 두 그룹으로 나눠 선택
  • 처리자 기록 — 조작을 수행한 관리자 · 인증 스트리머의 uid와 처리 시각을 함께 기록해 감사 추적(audit trail)이 가능하게 한다
왜 필수로 강제하나 — 조기 마감·무효 처리는 배당이 걸린 결과를 바꾸는 강한 권한이라, 사유·처리자 기록이 없으면 나중에 분쟁이 생겼을 때 왜 그런 조치를 했는지 추적할 방법이 없다. 04번 검수 화면의 예외 처리(추천수 · 참가자 미달 강제 승인)도 같은 원칙으로 처리자 기록이 남아야 한다.
감사 로그는 서버가 기록해야 진짜 감사 추적이 된다 — 사유 · 처리자 · 시각 기록은 클라이언트가 보여주기 위한 화면일 뿐, 실제 기록은 Cloud Functions가 처리 시점에 서버 측 로그(예: Firestore/RTDB 감사 노드 또는 Cloud Logging)에 직접 남겨야 신뢰할 수 있는 감사 추적이 된다. 클라이언트 로컬 저장소(localStorage 등)에만 남기면 본인이 임의로 지우거나 조작할 수 있어 분쟁 시 증거로 쓸 수 없다.

Security Rules 확장안 (bettingMarket 블록)

기존 rules.json의 최상위 노드(stocks, users, streamerVerifications 등)는 전혀 수정하지 않고, 같은 파일에 아래 블록만 추가한다. 잔액 · 배당 등 재화가 걸린 값은 클라이언트 write를 전부 false로 막아 Cloud Functions(Admin SDK)만 쓸 수 있게 한다.

"bettingMarket": { "markets": { ".read": "auth != null", "$marketId": { ".write": false } }, "bets": { "$marketId": { "$betId": { ".read": "auth != null && data.child('uid').val() === auth.uid", ".write": false } } }, "wallets": { "$uid": { ".read": "auth != null && auth.uid === $uid", ".write": false } }, "exchanges": { "$uid": { ".read": "auth != null && auth.uid === $uid", "$exchangeId": { ".write": false } } }, "reserveFund": { ".read": false, ".write": false }, "likes": { "$marketId": { "$uid": { ".read": "auth != null", ".write": "auth != null && auth.uid === $uid" } } }, "verifyRequests": { ".read": false, "$pushId": { ".write": "auth != null && !data.exists() && newData.child('uid').val() === auth.uid" } } }

위 bettingMarket 블록과는 별개로, 최상위 streamerVerifications 노드(주식시장과 공유)의 규칙도 다음과 같이 완화한다.

"streamerVerifications": { ".read": true, ← 기존 false에서 완화 (05번) "$id": { ".write": false } }
좋아요(likes) · 인증 신청(verifyRequests)만 클라이언트 write 허용 — 04번 라이트 검증(다수결)과 05번 인증 신청 접수는 실시간성이 중요해 Functions 왕복 없이 처리한다. verifyRequests는 본인 명의로 새 신청만 생성 가능하고 수정 · 삭제는 불가하다(!data.exists()). 승인 · 반려 · 해제(공유 streamerVerifications 쓰기)는 여전히 Cloud Functions(관리자 권한 확인)로만 가능하고, 읽기만 완화되었다.
호스팅은 기존 그대로 — 헤더에 명시된 대로 GitHub Pages를 유지하고, Firebase Hosting은 별도로 쓰지 않는다.

Cloud Functions ↔ 클라이언트 처리 구분

기준은 하나다 — 재화(잔액 · 풀 · 배당)가 움직이거나, 클라이언트가 위조할 수 있는 값(시간 · 권한)을 검증해야 하면 전부 Cloud Functions로 보낸다. 그 외 단순 조회 · 본인 좋아요만 클라이언트가 직접 처리한다.

uid 위변조 검증 원칙 — 모든 Cloud Functions는 요청 본문(payload)에 담겨 온 uid를 절대 신뢰하지 않는다. 대상 uid는 오직 Firebase Auth가 서버 측에서 검증한 호출자 컨텍스트(context.auth.uid)에서만 가져온다. 배팅 참가 · 취소 · 환전 · 인증 신청처럼 "본인 명의" 처리가 필요한 모든 기능에 동일하게 적용되는 공통 원칙이며, 07번 환전의 "대상은 항상 본인 uid" 규칙도 이 원칙의 한 사례다. 클라이언트가 자기 요청에 남의 uid를 써서 보내는 것 자체를 원천 차단한다.

잭팟 최종 사양 (12 · 14번 갱신)

  • 횟수 제한 — 유저당 하루 1회. 서버(Cloud Functions)가 lastJackpotDrawDate 값을 RTDB 트랜잭션으로 원자적으로 확인 · 갱신해 중복 도전을 차단한다
  • 당첨 확률 — 1/50. 당첨 시 그 시점까지 적립된 잭팟 잔액 전액을 지급하고, 잭팟 잔액은 0으로 초기화되어 다시 쌓이기 시작한다
  • 당첨 이력 — bettingMarket/jackpotWins에 당첨자 · 금액 · 시각을 기록해 다른 유저도 열람 가능(신뢰도 확보 목적)

  • 카카오 로그인 추가 — Google 로그인만 지원하던 것에서 카카오 로그인을 추가 지원한다
  • 익명 접근 허용 — 마켓 열람 등 일부 기능은 로그인 없이도 가능하도록 범위를 넓혔다
  • 신뢰 계정(isTrustedAccount) 개념 도입 — "실제 계정으로 로그인(Google/카카오, 익명 아님)" 또는 "관리자" 또는 "인증된 스트리머" 중 하나에 해당하면 신뢰 계정으로 간주한다. 인증 스트리머는 별도 실계정 로그인 없이도 환전을 포함한 모든 기능을 실계정 유저와 동일하게 이용할 수 있다 — "인증만 마치면 곧바로 정식 유저 대우를 받는다"는 원칙을 반영한 결정이다
  • 계정 정지(밴) 시스템 신설 — 관리자가 계정을 정지시키면 bettingMarket/bannedAccounts에 기록되고, 재화가 오가는 모든 기능(배팅, 환전, 인증 신청, 판정 등)의 진입 시점에 정지 여부를 서버가 항상 재확인해 차단한다

스트리머 인증 · 관리 흐름 확장 (05번 갱신)

  • 인증 여부 미러 노드 추가 — RTDB 보안 규칙은 인덱스 조회를 직접 지원하지 않으므로, "이 uid가 인증 스트리머인가"를 규칙에서 O(1)로 판별할 수 있도록 bettingMarket/verifiedStreamerUids/{uid} 미러 노드를 Cloud Functions가 인증 승인 · 해제 · uid 재신청 시마다 동기화한다 (클라이언트는 읽기 · 쓰기 모두 불가, Functions 전용)
  • 스트리머 추가 신청 큐 — 신규 방송국을 배팅 대상으로 올려달라는 bettingMarket/streamerRequests 신청 큐가 추가되어 관리자가 검수 · 승인 · 반려한다
  • 인증된 스트리머는 인증 신청 버튼을 보지 않는다 — 이미 인증이 승인된 계정에는 "스트리머 인증하기" CTA를 더 이상 노출하지 않는다
  • 인증 승인 시 빈 프로필 자동 채움 — approveVerification이 승인 시 bettingMarket/profiles/{uid}에 닉네임이 아직 없으면(프로필 자체를 한 번도 저장한 적 없으면) streamerVerifications의 닉네임 · SOOP 아이디 · 아바타로 초기값을 채운다. 이미 본인이 직접 정한 닉네임이 있으면 절대 덮어쓰지 않는다 — 랭킹 등에서 "유저XXXXXX" 폴백 대신 방송 닉네임이 바로 보이도록 하기 위함(13번 관련)

판정 유예 시간 (10번 갱신)

배팅 마감 후 정산까지 유예 시간을 두고, 유예 시간이 지나 자동 정산 처리가 일단 "확정 시작(finalizing)"되면 그 이후로는 관리자 · 인증 스트리머라도 판정을 되돌리거나 취소할 수 없다. 확정 처리 시작 여부는 RTDB 트랜잭션으로 원자적으로 판별해, 확정 처리와 수동 판정 · 취소 요청이 동시에 들어와도 이중 처리되지 않도록 한다.

관리 탭 · 감사 기능 확장

  • 관리자 전용 대시보드(가입 · 배팅 · 재화 통계, 시계열 차트, 이상 거래 모니터링, 환전 로그 열람)가 추가되어 관리 탭에서 열람 가능하다
  • 닉네임 신고 처리에 "무시" 액션이 추가되어(dismissNicknameReport), 마켓 신고와 동일한 방식으로 신고 건을 종료 · 감사 로그에 기록할 수 있다
  • 관리자 · 인증 스트리머 채팅이 추가되어(sendAdminChatMessage), 관리 탭 상단에서 서로 실시간으로 대화할 수 있다. 재화가 걸린 기능은 아니지만 다른 관리 전용 데이터와 동일한 원칙으로, 클라이언트가 bettingMarket/adminChat에 직접 쓰지 못하게 막고 Cloud Function을 거치도록 해 정지 계정 차단 · 메시지 길이 제한(300자)을 서버에서 항상 보장한다. 읽기 권한도 관리자 · 인증 스트리머로 한정된다
Security Rules 원칙 재확인 — chargeRequests · streamerRequests · verifyRequests · bannedAccounts는 관리자 이메일 계정만 읽을 수 있고, marketReports · nicknameReports · auditLog · adminChat는 관리자 또는 verifiedStreamerUids 미러 노드에 등록된 인증 스트리머만 읽을 수 있도록 좁혔다. 그 외 공개 열람이 필요한 blockedNicknames · profiles는 기존처럼 로그인 유저 전체에게 열려 있다.

관리 탭 검수 알림 배너

인증 스트리머 홍보 배너 바로 아래, 관리 탭 최상단에 검수가 필요한 항목(검수 대기 제안 · 마켓 신고 · 닉네임 신고, 관리자 전용으로는 인증 신청 · 충전 신청 · 스트리머 추가 요청)을 모아 알림 형태로 보여주고 총 건수를 배지로 표시한다. 각 항목 클릭 시 해당 섹션으로 스크롤 이동하며, 각 목록 DOM을 MutationObserver로 관찰해 검수가 완료되어 항목이 사라지는 즉시 알림도 함께 갱신된다(기존 렌더링 로직은 건드리지 않는 방식).

데이터 소모 최적화 — 실시간/1회성 구독 분리

마켓 피드가 bettingMarket/markets 전체를 통짜로 실시간 구독하면서, 정산 완료된(settled/void) 마켓까지 무제한으로 실시간 스트리밍하던 문제를 개선했다.

  • 아직 값이 바뀔 수 있는 4개 상태(pendingValidation/open/closed/pendingSettlement)만 상태별로 나눠 실시간 구독
  • settled/void는 절대 다시 안 바뀌므로 상태별 최근 30개만 1회성으로 조회. 다만 실시간 구독 중이던 마켓이 이 상태로 넘어가는 순간은 즉시 1회성으로 최신값을 받아와 "정산 확정 화면이 자연스럽게 넘어가는" 경험은 유지
  • 전체 방문자에게 걸리던 인증 스트리머 홍보 배너(streamerVerifications)도 1회성 조회로 전환하고, 관리 탭에 실제로 들어가는 소수(관리자 · 인증 스트리머)에게만 실시간 구독을 시작하도록 분리
  • auditLog(최근 처리 내역) · adminChat(관리 탭 채팅)은 기록 · 전송할 때마다 서버가 최근 200개를 넘는 오래된 항목을 실제로 삭제(functions/src/lib/capped-log.js)하고, 클라이언트도 limitToLast 쿼리로 필요한 만큼만 요청하도록 변경

좋아요 자동 오픈 기준 완화 (04번 갱신)

04번에서 확정했던 좋아요 20개 기준을 실제 운영 판단에 따라 10개로 낮췄다. 클라이언트 표시(진행률 · 안내 문구)와 서버 상수(LIKE_THRESHOLD)를 함께 갱신했다.

스킨 시스템 (설계 중 · 일부 구현)

보유 재화로 구매해 페이지 전체 룩을 바꾸는 신규 탭. 탭 레이아웃과 카테고리, 첫 스킨 카드(엑셀 기본 테마) 표시까지는 구현되어 있고, 구매 · 장착 · 미리보기 로직은 아직 미구현 상태다.

현재 접근 제한 — 스킨 탭은 아직 기능이 완성되지 않아 관리자 전용으로 숨겨져 있다(관리 탭과 달리 인증 스트리머도 제외). 완성 후 전체 공개 여부는 별도로 결정한다.

카테고리 · 첫 스킨

  • 카테고리는 전체 / 테마 두 가지로 단순화
  • 테마 스킨 — 프로필 · 닉네임 등 부분 커스터마이징이 아니라, 페이지 전체에 한 번에 적용되는 스킨. 카테고리당 유저는 1개만 장착 가능
  • 첫 스킨: 엑셀 기본 테마, 가격 200,000원. 엑셀 특유의 초록 리본 헤더 + 셀 그리드 배경, 밝은 배경에 진한 텍스트, Calibri, Segoe UI 계열 폰트로 페이지 전체를 리스킨한다

Cloud Functions

  • purchaseSkin({ skinId }) — requireAuth + assertNotBanned → SKIN_CATALOG에서 유효성 확인 → 이미 보유중이면 거절 → adjustBalance(uid, -price)(잔액 부족 시 예외) → ownedSkins에 기록 + skinPurchases에 이력 추가. 일반 구매 행위라 관리자 감사 로그(auditLog)에는 남기지 않는다(배팅 · 환전과 동일 원칙)

테마 적용 방식

이 앱은 색상 · 폰트를 이미 CSS 커스텀 프로퍼티(--ink, --panel, --gold, --font-body 등)로 관리하므로, 로그인 시 equippedSkin 값에 따라 document.documentElement에 theme-{skinId} 클래스만 붙이면 된다. html.theme-excel-default { ... } 블록에서 변수를 오버라이드하는 것만으로 기존 마크업 · JS를 전혀 건드리지 않고 페이지 전체가 즉시 리스킨된다(새로고침 불필요).

미리보기 (구매 · 장착과 분리된 클라이언트 전용 기능)

  • 보유 여부와 무관하게 항상 클릭 가능. 서버에는 아무 것도 기록하지 않고 그 순간 화면에만 테마 클래스를 씌운다
  • 미리보기 시작 시 화면 상단에 "미리보기 중 · (스킨명) · 미리보기 종료" 안내 바가 뜨고, 종료하거나 다른 스킨을 다시 미리보면 원래 상태(미장착이면 기본 테마, 장착중이었다면 그 테마)로 복귀한다
  • 새로고침 · 다른 탭 이동 시에는 미리보기 상태를 유지하지 않고 항상 리셋 — 실제로 적용된 상태(장착)와 혼동되지 않도록 하기 위함

스킨 카드 버튼 구성

카드마다 버튼 최대 2개: 미리보기(항상) + 상태별 버튼 — 미보유("구매하기") / 보유중 · 미장착("장착하기") / 장착중("해제하기").

관리 탭 — 스킨 구매 내역
